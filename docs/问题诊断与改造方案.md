# 浮生流年 — 问题诊断与改造方案

> 日期：2026-07-28
> 依据：backend/app 全部 59 个 py 文件 + backend/skills 16 个 SKILL.md 静态代码审查，对照《设计文档.md》v3.0 与部署清单。
> 三个症状：① 写出来不像真人写的；② 撑不起几百万字；③ 流程控制有问题。

---

## 一、结论摘要（先看这个）

**"不像真人写的"不是玄学，是四个可定位的技术根因叠加：**

| # | 根因 | 位置 | 严重度 |
|---|------|------|--------|
| 1 | 所有生成节点统一 **temperature=0.3**（因强制 JSON 输出触发低温分支） | `llm_client.py:62` | ★★★★★ |
| 2 | **整章正文被塞进 JSON 字符串**输出，模型在"写小说"和"保证 JSON 合法"之间分心 | 各 SKILL.md 末行 + `runtime.py` | ★★★★★ |
| 3 | Writer prompt 里 **20+ 条"禁止/不得"清单、零正面范例**，模型在守规矩不是在讲故事 | `skills/novel-writer/SKILL.md:20-41` | ★★★★ |
| 4 | Humanizer 是**机械删词**（`"总之"→""` 直接删除，留残句破坏语法），不是 LLM 改写 | `humanizer.py:6-22` | ★★★ |

**"撑不起几百万字"的根因：长程记忆机制一半是空壳：**

- 冷热分层从不生效（实体永远 hot，无衰减逻辑）；
- 滚动摘要链**根本没实现**，远端剧情只靠"最近 5 章 summary + 尾段"；
- 前章尾段设计说 2000 字，实际只注入 **700 字**（`context.py:247-249`）；
- pgvector 向量检索默认无 embedding key → **开箱即静默失效**，退化成单轨 FTS；
- 卷末再规划不自动触发，且有过滤 bug 导致已发布章节丢失。

**"流程控制有问题"的根因：两个结构性 bug：**

- **Guardian 失败→重做 Architect 的循环在结构上不可能成立**：节点按 input_hash 缓存，重试时 Architect 命中缓存被跳过 → 同一份 beat sheet 反复送审 → 3 次后章节永久 failed（`pipeline.py:163-176, 312-313`）；
- **"九道质量门"只有 1 道真正阻断**，其余全是 `blocking=False` 的装饰（`quality.py:180-237`）；而那 1 道一旦失败就把整本书 `paused`（`publisher.py:206-216`）——要么形同虚设，要么一票停更，没有中间态。

另外一个**高危遗漏**：生成节点从不传 `max_tokens`（`runtime.py:472`）。很多 OpenAI 兼容网关对未指定 max_tokens 用较小默认值 → **正文可能被中途截断成残句**，这会直接表现为"写得莫名其妙"。

## 二、为什么不像真人写的（详细）

### 2.1 温度 0.3 是文风杀手

`llm_client.py:62`：`temperature = 0.3 if response_format=="json" else 0.75`。所有生成节点都要求 JSON → 全部走 0.3。低温输出高度确定、模板化，是"AI 味"最直接的推手。小说正文节点应该在 **0.8~1.0**。

### 2.2 JSON 包正文是系统性伤害

Writer 要求 `只输出 JSON：{content, summary, ...}`：
- 4000 字正文的引号、换行全部要转义，token 浪费且易产生转义破坏的标点；
- 模型的注意力被"格式合法性"分走；
- 叠加 0.3 低温（正是 JSON 模式触发的），双重伤害。

### 2.3 规则轰炸 + 零范例

`novel-writer/SKILL.md` 有 20+ 条"禁止"（禁止百科式讲解、禁止排比、禁止空泛总结…）。LLM 对"不要做什么"的遵循远差于"照这个样子写"。且：
- **没有一段正面范例**锚定文风；
- 设计文档吹的"九卡叙事学协议"在全代码库只有 SKILL.md 第 3 行一句空引用，**没有任何定义或注入逻辑**——是幽灵功能；
- system prompt（整篇 SKILL.md 规则）+ user 消息（整个 context_pack 的 `json.dumps`）都很庞大，**没有任何地方核算真实 token**，叙事上下文被规则和 JSON 结构挤占。

### 2.4 Humanizer 反而在制造 AI 味

`humanizer.py` 全文 55 行：7 条 `str.replace` 词表（多数是**整词删除**）+ 合并空行。"…总之，战争结束了" → "…，战争结束了"。计算指标里 TTR 按"字"算（中文几乎无区分度）、无 perplexity、无结构指纹模型；**指标算完只记录、从不触发重写闭环**。设计文档说的"计算级去 AI 味 + 不达标 LLM 重写"完全没实现。

### 2.5 摘要驱动续写导致叙事声音断裂

Writer 每章实际拿到的"前文"只有：前章末 700 字 + 最近 5 章的 summary。等于**永远在"读了梗概就续写"**，人物语感、叙事声音跨章漂移是必然的。

## 三、为什么撑不起几百万字（详细）

| 设计宣称 | 实际状态 | 证据 |
|---|---|---|
| 冷热分层 + 实体温度 | **空壳**：只写 "hot"，无任何降温逻辑，过滤条件永远全命中 | `state_log.py:30-43`、`context.py:116` |
| 滚动摘要链（章→段→卷） | **不存在** | 全库无对应代码 |
| 前章尾段 2000 字 | 实际 700 字 | `context.py:247-249` |
| pgvector 混合检索 | 结构真实，但默认无 embedding key → 静默退化为 FTS 单轨 | `config.py`、`indexing.py:159-180` |
| 每 50 章 Wiki 审计 | 只有手动管理接口，流水线从不自动触发 | `wiki.py:165-185`、`api/memory.py:64` |
| 卷末自动再规划 | LLM 逻辑真实（`replan.py`）但 ①auto_write 从不触发它；②过滤 `["draft","confirmed"]` 漏掉已发布的 `"completed"` 章 → 简报丢最近上下文 | `replan.py:34`、`publisher.py:263` |
| Observer×3 + Verifier 交叉验证 | 只在"导入分析"里用，**生成流水线从不调用**，状态提取只靠单个 state-extractor | `pipeline.py:219-284`（定义了没人调） |
| 活体 Wiki / 伏笔生命周期 / TOC 树 | ✅ 这三块实现得不错 | `wiki.py`、`publisher.py:297-324`、`retrieval.py:391-448` |

**叠加效应**：context pack 不随篇幅"瘦身"（冷分层失效），远端剧情无摘要链可查，RAG 大概率没向量轨，卷规划靠手动——写到几十万字后"忘设定、人物走形"是结构性必然。

## 四、流程控制问题（详细）

1. **Guardian 死循环→永久 failed**：Guardian FAIL 直接 `raise RuntimeError`（`pipeline.py:312-313`），coordinator 整条重跑；但 `_run_node` 按 `input_hash` 缓存已完成节点（`pipeline.py:163-176`），Architect 输入没变 → 命中缓存跳过 → beat sheet 一个字不变再送 Guardian → 必然再挂 → 3 次后章节 `failed`、项目 `paused`。
2. **质量门形同虚设**：13 个 gate 只有 `narrative_hard_failures` 一个 `blocking=True`；字数、反 AI、风格、POV、伏笔、一致性全部只记录不拦截。
3. **一票停更**：唯一阻断门失败 → `project.status="paused"` + `auto_write=False`。critic 判一条 hard_issue，整本书停，每次都要人工救。
4. **无 max_tokens 保护**：`runtime.py:472` 调 `complete` 从不传 max_tokens，长章随时可能被网关默认值截断。
5. **input_hash 缓存哲学错误**：LLM 节点"同输入必同输出"的假设不成立，缓存会固化一次劣质输出，并阻断一切"重跑上游"的修复语义。

## 五、改造方案

### P0 — 改动小、见效大，先做这四件（直接决定"像不像人写"）

**P0-1 拆掉正文的 JSON 枷锁 + 提温 + 设 max_tokens**
- Writer/Editor 输出改为**纯文本正文**（summary 等元数据用第二次轻量调用提取，或用 `<<<META>>>` 分隔符约定，别用 JSON 包正文）；
- `llm_client.py`：温度按节点配置——writer/editor 0.85~0.95，architect/planning 0.6，guardian/critic/extractor 0.2（这些保留 JSON）；
- `runtime.py::run_agent_node` 显式传 `max_tokens`（writer ≥ 8192），并加配置项。

**P0-2 重写 Writer prompt：规则减法 + 范例加法**
- "禁止清单"从 20+ 条压到 ≤5 条最关键的；
- 加入 1~2 段**目标文风的正面范例段落**（few-shot 锚点，可从你欣赏的作家段落改写）；
- "九卡叙事协议"要么删掉这句空话，要么真正做成注入模板；
- context_pack 不要整坨 `json.dumps` 丢进去，改为**分节渲染成自然语言简报**（"前情：…/本章要写：…/在场人物状态：…"），并用真实 tokenizer（如 tiktoken）核算总 prompt token。

**P0-3 Humanizer 改为 LLM 改写节点 + 指标闭环**
- 删掉机械删词表（至少删掉所有 `→""` 的整词删除）；
- 新增 LLM 改写 pass：高温、纯文本进出、prompt 只给"重写目标"不给禁词表；
- `calculate_anti_ai_scores` 保留做门控：不达标 → 触发一次定向重写（把超标指标写进重写指令），最多 1 轮，仍不达标则标记降级人审——**形成闭环**而不是只记录。

**P0-4 修 Guardian 重试缓存 bug**
- `_run_node` 的 input_hash 加入 `attempt` 序号（或对修复型重试显式 bust cache）；
- 真正实现反馈循环：Guardian FAIL 时把失败理由注入 Architect 的重跑 payload，最多 2 轮，仍失败才 fail 整章。

### P1 — 长篇支撑（决定"能不能写到几百万字"）

**P1-1 实现滚动摘要链**：章摘要（已有）→ 每 10 章"段摘要"（发布第 10n 章时由 LLM 聚合）→ 卷摘要（卷末生成）。context pack 注入：本卷摘要 + 当前段摘要 + 最近 5 章摘要 + 前章尾段。
**P1-2 前章尾段恢复到 1500~2000 字**（`context.py:247-249`），这是叙事声音连续性的命根子。
**P1-3 实体温度真实衰减**：发布章节时按 `current_chapter - last_referenced_chapter` 降级（>30 章 → warm，>100 章 → cold），冷分层才真正给 context 瘦身。
**P1-4 修卷再规划**：`replan.py:34` 过滤加上 `"completed"`；auto_write 循环在卷边界（本卷最后一章发布后）自动触发 `generate_next_volume_plan`，生成的卷纲进"待确认"而不是直接开写。
**P1-5 配置 embedding 服务**：部署清单里没有任何 LLM/embedding key——先确认生产环境到底配了什么模型；embedding 可用硅基流动/智谱等便宜服务，否则向量检索永远静默失效。建议 `readyz` 里加"embedding 未配置"的显式告警，杜绝静默退化。

### P2 — 流程与架构（提质 + 稳定）

- **质量门分级**：致命门（一致性硬冲突、截断检测）blocking + 自动重写 1 次；重要门（字数、反 AI、POV）失败 → 该章标 `review_required` 但**不暂停整本书**，auto_write 继续写下一章；
- **Writer 分场景生成**：按 beat 分 2~3 次调用再拼接（每次带上一 beat 已写正文），比整章单次调用更可控、不易撞 token 上限；
- **Observer/Verifier**：要么接入生成流水线做状态交叉校验，要么删代码——别留幽灵；
- **每 50 章审计**接入 worker 定时任务；
- **模型路由**：writer 用强创作模型，guardian/extractor 用便宜模型（`llm_planning_model` 的机制扩展到核心 DAG）。

### 建议实施顺序

```
第 1 步：P0-1 + P0-4（一天内可完成，立刻解决截断、卡死、低温三大硬伤）
第 2 步：P0-2 + P0-3（prompt 工程 + humanizer 重做，用同一章素材 A/B 对比验证）
第 3 步：P1 全部（长篇支撑，写到 50 章前完成即可）
第 4 步：P2 按需
```

## 六、部署环境注意点

- 主力阿里云机只有 **2GB 内存**，已跑 Postgres + MinIO + Nginx + guagua；再上 FastAPI + worker + Next.js + pgvector 会很紧张（pgvector 索引吃内存）。**建议把小说系统部署到腾讯云 4GB 那台**（server.example.com，目前只有 SillyTavern）。
- 部署清单里**没有 LLM API key 记录**——生成质量诊断的前提是确认生产用的什么模型；若用的是低价小模型，P0 改完后建议 writer 节点换更强的创作模型再对比。
- ⚠️ 安全提醒：清单里 root/GitHub 密码、Gitee token 均为明文，且本文件曾被多方工具读取，建议近期轮换关键密码。

## 七、验证方法（改完怎么知道有效）

1. 固定同一章纲，改造前后各生成 3 版，盲评"像不像人写"；
2. 检查发布链路：人为让 guardian 判 FAIL，确认 architect 真的带失败理由重跑且 beat sheet 有变化；
3. 长跑测试：mock 之外用真模型连写 30 章，检查第 30 章 context pack 里是否含段摘要、实体温度是否有 warm/cold、卷末是否自动出卷纲；
4. 在 `quality_scores` 里跟踪 anti_ai 指标趋势，确认 humanizer 闭环生效。
