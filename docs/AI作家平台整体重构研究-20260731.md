# AI 作家平台整体重构研究（2026-07-31）

> 本文基于当前仓库代码，而不是只依据此前设计文档。它用于取代“继续往固定流水线里加节点”的思路，给出可渐进迁移、可验收的目标架构。

## 1. 结论

当前项目没有“彻底崩掉”。durable worker、不可变 revision、状态事件、Current State、Wiki、混合检索、PageIndex、摘要链、伏笔账本和 SSE 都是能继续使用的资产。真正的问题在创作控制面：系统已经有很多角色，却仍是一条固定 DAG；它能把任务跑完，但没有一个角色对作品整体负责，也不会从作者的选择和改稿中持续学习。

因此答案不是简单改成“更多 Agent”。推荐架构是：

**一个主笔 Agent 拥有正文，三个受约束的专职角色提供策划、连续性和读者反馈，由持久化章节状态机编排；角色之间只交换有 schema、版本和来源的创作工件，不互相自由聊天。**

保留 FastAPI、PostgreSQL、worker 和现有 Canon 底座。替换固定章节 DAG、全章多轮改写、单一 Context Pack、空壳反馈域和前端“大表单 + 黑盒生成”体验。

目标不是“自动生成几百万字”，而是做到：

1. 每一章都承接具体的人、具体的欲望和上一章留下的心理余波。
2. 写到百万字后仍能说清事实、承诺、因果、关系和人物声音为什么如此变化。
3. 作者每次采用、拒绝、改写和批注都会改变下一章，而不是成为一次性操作。
4. AI 给出的是可选择的故事行动，不是直接倾倒四千字成稿。
5. 系统用人类盲评和长期一致性测试证明质量，而不是相信模型自报分数。

## 2. 当前实现的真实状态

### 2.1 已经修好的问题

此前文档中提到的几个 P0 问题已经落地：

- Writer/Editor 已走纯文本输出，正文不再包在 JSON 中（`engine/runtime.py:619-650`）。
- Writer/Humanizer 温度已提高，结构任务保持低温（`engine/runtime.py:446-452`）。
- 正文已显式设置 `max_tokens`（`engine/runtime.py:645-650`）。
- Guardian 反馈会注入 Architect，并绕过旧缓存（`engine/pipeline.py:388-414`）。
- 前章结尾已扩到 2000 字，并有滚动摘要和长程摘要（`engine/context.py:505-527`）。
- 质量门已经区分阻断项与软提示（`engine/quality.py:214-257`）。

这些基础工作应保留，不要再次推倒重写。

仍未修复的一项旧问题是：`_run_observers` 虽然在 `engine/pipeline.py:302` 定义，
正文 pipeline 并未调用它；Verifier 主要出现在导入分析旁路。当前章节发布前仍主要依赖单个
state extractor。这也说明“代码里有角色”不等于“生产链路真正使用了能力”。

### 2.2 仍然导致“流水线机器感”的结构原因

#### A. 多角色不等于多 Agent，更不等于创作共同体

当前每章仍按 `world-simulator -> architect -> guardian -> writer -> humanizer -> critic -> editor -> critic -> extractor` 顺序执行。角色没有独立的长期目标、记忆或决策权限，只是同一个模型在不同 prompt 下依次转换 JSON。

直接后果是：

- 上游错误会被包装后继续向下传播。
- 每个节点都倾向于满足自己的局部 rubric，没有角色对整章的灵魂和整本书的终局负责。
- “角色更多”带来延迟和成本，却不自动带来观点多样性；同模型、同上下文、相似 prompt 常产生相关性很高的判断。
- 失败后多数是重做相邻节点，不是真正回到错误决策发生的位置。

#### B. 正文经过多次全量改写，作者声音被平均掉

Writer 之后固定运行 Humanizer；Critic 命中问题后，Editor 再输出完整正文，随后又运行一次 Humanizer。全章改写每多一次，人物措辞、节奏毛边和有意的不规则越容易被统一成“正确但平”的平均文风。

Humanizer 当前 prompt 还要求“把 AI 初稿改得更像真人”，但它并不知道作者真正认可过哪些句子。它只能依据通用规则重写，因此不应成为固定必经节点。

#### C. Context Pack 是资料袋，不是经过冲突消解的创作上下文

当前实现已经做了节点裁剪，但仍将 `model_payload` 整体 `json.dumps` 给模型（`engine/runtime.py:647`）。`token_budget` 实际按 JSON 字符数计算，不是真实 token；而且一个检索 query 同时拼接目标、钩子和人物名，很难分别回答以下问题：

- 这个人物此刻知道什么？
- 两个人上次关系发生改变的原文在哪里？
- 当前开放承诺中哪一条必须推进？
- 本书被作者认可的句法和对话声音是什么？

资料有优先级列表，但缺少逐条 provenance、有效章节范围、冲突状态和“为什么本章需要它”。模型仍要自己在大量异构 JSON 中做最后一次数据治理。

#### D. 长篇记忆偏“事实”，缺“戏剧状态”

现有 Canon、Current State、Wiki 对人物位置、物品和设定很有价值；`PlotLedger` 主要覆盖伏笔。但小说连贯不仅是“不穿帮”，还需要持续维护：

- 人物当前欲望、恐惧、误解、羞耻、未说出口的话；
- 选择为什么发生，造成了什么立即后果和延迟压力；
- 读者正在等待哪些承诺，最近一次被提醒是什么时候；
- 关系中的权力、亲疏、亏欠和信任怎样变化；
- 每个角色特有的观察方式、措辞、回避方式和沉默方式。

现有 `TasteProfile`、`FeedbackEvent`、`DecisionPoint`、`CharacterVoiceCard` 和 `StyleExemplar` 已建表，但几乎没有进入 API、生成上下文和发布事务。这些是“设计落库、产品未通电”的典型断层。

#### E. Beat Card 存在，但没有成为默认创作入口

后端和蓝图客户端已经支持 BeatCard；章节流水线在没有章纲 beats 时甚至会自动生成卡。但日常 Workspace 仍主要让用户确认章纲后直接“开始写作”。用户看不到人物为什么这么做、局面如何改变、哪项承诺被推进，也无法在低成本阶段纠偏。

#### F. 前后端模块边界过大

`services/ai_assist.py` 约 2700 行，`models/entities.py` 约 1150 行，`schemas.py` 约 790 行，`workspace/[id]/page.tsx` 约 740 行。它们横跨多个业务域，导致每加一个创作状态都要穿过巨型模块，最终倾向于继续塞字段而不是形成清晰生命周期。

### 2.3 当前测试能证明什么、不能证明什么

当前后端 155 个测试通过，前端生产构建通过。这证明基础契约和工程可运行，但不能证明小说好看。现有测试主要验证 schema、状态和 API；缺少固定素材的跨章生成回归、人工盲评、角色声音识别和 50/200 章长期一致性评测。

## 3. 多 Agent 的正确用法

### 3.1 推荐的四个责任角色

| 角色 | 长期责任 | 可以写什么 | 不可以做什么 |
|---|---|---|---|
| 主笔 Lead Writer | 作者心意、人物生命感、最终正文 | 场景稿、整章稿、接受后的局部补丁 | 自行修改 Canon、替作者决定重大转折 |
| 故事策划 Story Director | 卷/事件弧/本章戏剧选择 | 2-3 个 Story Move、Scene Contract | 写最终正文、用套路覆盖已确认意图 |
| 连续性编辑 Continuity Editor | 事实、知识边界、因果、承诺与关系连续 | 冲突报告、必要证据、最小修复约束 | 泛化文风偏好、整章润色 |
| 读者编辑 Reader Editor | 可读性、情感兑现、困惑点 | 带引用的阅读报告、可选软建议 | 用自报总分阻止发布、直接重写正文 |

World Simulator 不必作为独立人格。它更适合作为 Story Director 的结构化工具：输入人物状态，输出各人在本场景的欲望、可知信息、选择倾向和冲突。Observer/Extractor 也应是发布后的抽取工具，不应假装创作角色。

### 3.2 为什么不能让 Agent 自由群聊

自由群聊会产生冗长上下文、责任模糊、不可复现和成本失控。生产系统应使用“黑板架构”：所有角色读写同一组版本化工件，每次动作都有输入版本、输出版本、模型、prompt、证据和决策者。

```text
Author Intent / Canon / Story State
               |
       Orchestrator State Machine
               |
  Story Move -> Scene Contract -> Manuscript Revision
       |              |                  |
  user choice   continuity preflight   reader report
       |              |                  |
       +------ Decision & Feedback Log --+
                         |
              distilled project memory
```

### 3.3 Agent 何时才应被调用

- 默认只调用一次策划、一次主笔、一次连续性检查。
- 只有出现新重大决策时才停下来请求作者；已存在相似决策时可按项目控制档自动处理。
- 只有带逐字证据的 hard issue 才触发一次局部 Repair。
- 软问题默认展示，不自动改稿。
- 同一模型可以承担多个角色，但关键审计最好与 Writer 使用不同模型族，降低相关性偏差。

## 4. 目标后端架构

### 4.1 按业务域拆分，而不是按“AI 功能”堆服务

建议逐步形成以下包：

```text
app/domains/
  projects/       # 项目、作者意图、控制模式
  blueprint/      # L0-L5、卷、事件弧、Story Move
  manuscript/     # 章节、场景、revision、patch、发布
  story_state/    # Canon、Current State、关系、知识边界
  promises/       # 读者承诺、伏笔、悬念、兑现窗口
  memory/         # 摘要、PageIndex、检索、上下文编译
  feedback/       # diff、选择、批注、蒸馏规则、范例
  evaluation/     # 硬检查、读者报告、离线基准
app/orchestration/
  chapter_machine.py
  activities/
  policies/
app/agents/
  story_director.py
  lead_writer.py
  continuity_editor.py
  reader_editor.py
```

API 只处理认证、命令和查询；domain service 维护业务不变量；orchestrator 只推进状态；agent adapter 只负责模型 I/O。`ai_assist.py` 不再继续增长。

### 4.2 用章节状态机替换固定 DAG

```text
IDEA
 -> MOVES_PROPOSED
 -> MOVE_SELECTED
 -> SCENE_CONTRACT_READY
 -> PREFLIGHT_PASSED
 -> DRAFT_READY
 -> CONTINUITY_REVIEWED
 -> REPAIR_OPTIONAL
 -> AUTHOR_REVIEW
 -> PUBLISHED
 -> STATE_COLLECTED
```

每个状态都保存工件 ID，而不是把所有内容嵌套进一次 run payload。状态边由 policy 决定：自动挡可自动选择低风险 Story Move，副驾挡默认停在 Move/Contract，手动挡每一步停留。

失败必须回到产生错误的状态：

- 目标或情节不成立：回到 `MOVES_PROPOSED`。
- 人物动机不足：回到 `SCENE_CONTRACT_READY`。
- 正文漏场景：回到 `DRAFT_READY` 做最小补丁。
- Canon 冲突：修正文或明确申请修改 Canon，不能让 Critic 自己选择。

### 4.3 新增四类一等工件

#### Story Move

一章开写前给 2-3 个真正不同的行动方向，而不是三种措辞版本。字段包括：主角行动、对手反应、即时得失、关系变化、承诺推进、风险、为何符合作者意图。

#### Scene Contract

每场只保留对写作有用的字段：

```json
{
  "entry_state": "从前章哪个未完瞬间进入",
  "pov": "视角人物",
  "desire": "此刻具体想得到什么",
  "opposition": "谁或什么阻止",
  "knowledge_boundary": ["已知", "误以为", "未知"],
  "turn": "什么新事实或选择改变局面",
  "exit_state": "结束时事实和关系怎样改变",
  "emotional_residue": "人物带往下一场的余波",
  "promise_movement": ["推进/提醒/兑现/放弃"]
}
```

#### Manuscript Patch

Editor 不再全章重写。Patch 必须指出 revision、字符范围或段落 ID、原文哈希、问题证据、替换文本和预期效果。应用前检查哈希，避免用户已改稿后覆盖。

#### Feedback Distillation

把原始编辑 diff、选项选择、保留/撤销 patch、评分和批注蒸馏成候选规则。规则包含适用范围、正例、反例、置信度和证据事件 ID；连续多章得到验证后才激活，作者可查看、修改和禁用。

### 4.4 把长篇记忆升级为五本账

1. **事实账**：位置、物品、伤势、身份、世界规则和知识边界。沿用 StateEvent/CurrentState/Wiki。
2. **因果账**：关键选择 -> 直接结果 -> 延迟压力 -> 所属事件弧。
3. **承诺账**：读者问题、关系期待、升级目标、谜团和伏笔；记录提出、提醒、兑现窗口、状态。
4. **关系账**：双方信任、权力、亲疏、亏欠、秘密和最近改变证据。不要只存一个抽象“好感度”。
5. **声音账**：人物常用句法、称呼、回避方式、观察偏好和在不同关系下的说话变化；只从已发布正文和作者认可片段提取。

所有状态项必须带 `source_revision_id + evidence_span + valid_from_chapter + confidence + status(confirmed/disputed)`。抽取冲突进入 disputed 队列，不因 Observer 投票自动成为 Canon。

### 4.5 Context Compiler 取代通用 Context Pack

不要把仓库中的一切都交给模型。先根据任务编译最小充分上下文：

- `planning_context`：作者意图、当前卷/弧、五本账、最近重大选择。
- `writing_context`：Scene Contract、前章精确尾部、相关人物关系原文、声音范例、必要 Canon。
- `continuity_context`：待核断言及其 provenance，不需要写作教程。
- `reader_context`：正文、章纲承诺、目标读者和少量必要前情，不给答案式内部推演。

检索拆成多路 query 后用业务规则合并：人物历史、关系历史、开放承诺、世界事实、相似声音范例各自检索，不能只用一个拼接 query。预算用 provider tokenizer 或可校准的 token estimator 统计；日志记录每个片段入选/被裁剪的原因。

最终给 Writer 的输入应渲染为稳定、可阅读的 Markdown 创作简报，结构化 ID 放在引用标记中；避免让模型从深层 JSON 中自行判断主次。

### 4.6 发布语义拆成“可读稿”和“Canon 提交”

正文生成成功就保存 `draft_ready`，不应因为抽取或软审稿失败而让用户等不到稿。随后：

- 硬冲突存在：稿件可读，但不能提交 Canon。
- 软问题存在：允许发布并展示建议。
- 状态抽取失败：标记 `state_pending`，由后台重试，不覆盖正文。
- 作者手改后发布：从最终人工 revision 重新抽取，旧生成稿不得进入 Canon。

## 5. 目标前端体验

### 5.1 工作区围绕作者决策，不围绕 Agent 节点

主工作区建议保持三个稳定区域：

- 左侧：章节/卷/事件弧导航和开放承诺提示。
- 中间：正文编辑器，始终是视觉和交互中心。
- 右侧：随当前状态切换的“本章导演台”，显示 Story Move、Scene Contract、连续性证据或读者反馈。

用户不需要看到 `world-simulator`、`critic-recheck` 等内部节点名。进度用创作语言表达：正在找本章方向、正在写初稿、正在核对前后文。

### 5.2 默认章节流程

1. AI 给出 2-3 个“这一章人物可以怎么做”的方向，每个方向展示得失和风险。
2. 用户选一个，系统生成最多 3 个 Scene Contract；用户只改欲望、转折、结果和余波。
3. 主笔生成一版完整正文；前端可以流式展示，但最终以 revision 落库。
4. 右侧按证据显示连续性问题和读者困惑；软建议由用户逐条接受，禁止静默全章覆盖。
5. 用户编辑、接受 patch 或发布时，系统捕获反馈事件。

自动挡可以跳过 1、2 的停留，但仍保存工件；作者随时能看到“AI 为什么这样写”和回到决策点重开分支。

### 5.3 必须补齐的前端能力

- Story Move 对比，而不是只提供“换一版章纲”。
- Scene Contract/Beat Card 成为 Workspace 的默认可见步骤。
- 版本 diff、段落级接受/拒绝、恢复和分支。
- 事实/承诺/关系冲突的原文证据跳转。
- “我喜欢这段 / 这不像他 / 太解释 / 节奏太快”等低成本反馈。
- 项目记忆中心：作者能查看系统学到了什么，并撤销错误规则。
- 生成追踪页：模型、耗时、token、检索来源、失败原因面向调试，不污染普通写作界面。

### 5.4 前端代码拆分

把 `workspace/[id]/page.tsx` 拆成 route shell、server-state hooks 和领域组件。服务端状态推荐使用 TanStack Query（或保持现有栈时先封装等价 hooks），Zustand 只保存短期 UI 状态，避免页面组件同时管理请求、SSE、生成状态、编辑器和弹窗。

建议组件边界：`ManuscriptEditor`、`ChapterNavigator`、`StoryMovePicker`、`SceneContractEditor`、`EvidenceReview`、`RevisionHistory`、`GenerationInspector`。API contract 从 OpenAPI 生成类型，减少 `frontend/lib/api.ts` 外散落的手写 shape。

## 6. 质量系统必须重建为评测系统

### 6.1 在线门禁

硬门只处理可证实且真的不应入 Canon 的问题：明确事实冲突、知识越界导致行动、必写事件缺失、因果断裂、无铺垫背叛核心动机、作者红线、明显截断。每项必须引用原文和来源事实。

文笔、节奏、对白、POV、字数和“AI 味”是软建议，不能由脆弱正则或模型分数决定发布。`anti_ai` 指标可以用于观察趋势，不应作为“像不像人”的真值。

### 6.2 离线基准

建立仓库内版本化 `evaluation/cases`：

- 20 个不同题材的单章 Scene Contract。
- 10 组跨 3 章承接样本。
- 5 组跨卷事实/承诺召回样本。
- 人物声线辨识集：隐藏名字后判断对白属于谁。
- 故意注入的事实、知识边界和因果错误集。

每次 prompt、模型、检索或流程修改，固定随机种子和配置生成候选，保存成本与耗时。自动指标只筛硬错误，最终用盲评比较：更想继续读、人物是否活、是否看得懂、情感是否抵达、是否像同一本书。

### 6.3 生产反馈指标

真正有价值的指标包括：首稿直接采用率、作者修改字符比例、被撤销 patch 比例、重生成率、每章决策停留时间、跨章冲突率、开放承诺逾期率、人物声线混淆率、每千字成本和 P95 等待时间。不要把模型自报 82 分当产品质量 KPI。

## 7. 渐进迁移计划

### Phase 0：先建立质量基线（1 周）

- 从现有项目匿名选取“好/坏/驴唇不对马嘴”章节，建立首批盲评集。
- 记录当前链路调用次数、token、耗时、首稿采用率和人工改动比例。
- 为每个 Agent 输出记录模型、prompt hash、context manifest 和来源。
- 冻结继续添加通用规则和质量门，除非它能修复基准中的具体失败。

验收：同一章纲可重复跑当前版本，结果和成本可比较。

### Phase 1：停止过度改写（1-2 周，最高优先级）

- Humanizer 从固定必经节点改为用户可选或只在明确软问题时触发。
- Editor 改为 Manuscript Patch，不再默认全章重写。
- 保留一次 Writer、一次 Continuity Review；Reader Review 异步运行。
- 硬问题最多一次修复，软问题不自动修。

验收：正常章节只有一次正文生成；作者能看到并逐条接受修改；基准中人物声音不低于旧版，成本和耗时显著下降。

### Phase 2：打通“心意 -> 选择 -> 反馈”（2-3 周）

- 实现 Story Move API/UI 和章节状态机前半段。
- 把 BeatCard 升级为 Scene Contract 并接入 Workspace。
- 所有用户选择、编辑 diff、接受/拒绝 patch 写入 FeedbackEvent。
- 实现 tentative 反馈蒸馏和作者可管理的项目规则。

验收：作者改过三章后，系统能列出带证据的偏好，并在第四章上下文中实际使用。

### Phase 3：五本账与 Context Compiler（3-5 周）

- 在现有 StateEvent 旁新增 causal/promise/relationship/voice projection。
- 检索拆成多路 query，加入 provenance 和 disputed 状态。
- Writer 改读 Markdown 创作简报；按真实 token 预算。
- 从已发布且被作者保留的正文提取声音范例。

验收：50 章回归中能准确回答人物知识、关系变化、未兑现承诺及其证据；修改旧章后投影可重建。

### Phase 4：完整状态机与前端分支（3-4 周）

- worker 从 `pipeline.py` 固定 DAG 迁移到持久状态机。
- 增加 revision 分支、Story Move 回退和重大决策暂停策略。
- 拆分 Workspace 巨型页面和后端巨型 service。
- 旧 pipeline 保留 feature flag，完成 A/B 后删除。

验收：worker 任意状态崩溃可恢复；回到某个决策点不会污染已发布 Canon；新旧项目都可迁移。

### Phase 5：长跑与模型路由（持续）

- 用 50、200 章模拟项目做检索和投影压力测试，不必用模型真的生成全部正文。
- Writer、策划和审计按能力路由不同模型，建立每个题材的成本/质量矩阵。
- 每次生产模型升级先过离线基准和小流量项目。

## 8. 保留、替换、删除清单

| 当前能力 | 决策 | 说明 |
|---|---|---|
| FastAPI + PostgreSQL + durable worker | 保留 | 可靠性底座正确 |
| ChapterRevision + StateEvent + outbox | 保留并扩展 | 是可重建 Canon 的基础 |
| Wiki / CurrentState / Summary / PageIndex | 保留并校准 | 增加 provenance、多路检索和评测 |
| PlotLedger | 扩展为 Promise Ledger | 伏笔只是读者承诺的一类 |
| fixed `pipeline.py` | 渐进替换 | 迁移为工件驱动状态机 |
| World Simulator Agent | 降为工具 | 并入 Story Director 的结构活动 |
| Guardian | 合并 | 确定性检查进 preflight，事实检查进 Continuity Editor |
| Humanizer 固定 pass | 删除 | 改为显式可选 patch |
| Critic 自报总分 | 降级 | 只保留证据化 reader report |
| Observer 三路投票 | 简化 | 抽取可并行，但冲突进入 disputed，不以投票成真 |
| Taste/Feedback/Decision/Voice 表 | 真正接通 | 若两个阶段内仍不使用，就删除而不是继续做空壳 |
| 写作教程 RAG | 离线编译为方法卡 | 不把随机教程原文塞给 Writer |

## 9. 最先应该做的三个改动

如果只投入两周，不要先重做全部前端，也不要继续加 Agent。按这个顺序：

1. **取消固定 Humanizer 全章改写，Editor 改为证据化局部 patch。** 这会最快减少“越修越像机器”的问题。
2. **把 BeatCard/Scene Contract 放进 Workspace 的章纲与正文之间。** 让用户在两百字成本处修正人物欲望、转折和余波，而不是在四千字后返工。
3. **打通 FeedbackEvent：记录用户最终保留的正文 diff，并在下一章 Writer Context 中注入最近验证偏好和正面范例。** 这是从生成器变成“越来越懂作者的 AI 作家”的最小闭环。

完成这三项后再做五本账和完整状态机。否则现在直接上自由多 Agent，只会把现有流水线扩大成更贵、更慢、更难调试的流水线。
