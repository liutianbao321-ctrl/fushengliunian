# 创作流程与写作知识库改造

更新时间：2026-07-23

## 1. 研究范围与结论

本次抽样阅读了写作指导库中的写作动机、情节设计、人物设定、对话、节奏、伏笔和大纲材料。没有把旧教程中的商业偏见或题材套路直接当成系统规则，只提取可验证的方法。

主要结论：

1. 写作目的决定取舍。系统必须先保存作者为什么写、想给读者留下什么、不可妥协项，而不能只收集题材和爽点。
2. 情节不是事件列表。可写场景至少要有地点、人物即时欲望、阻力、行动、冲突、结果，结果还要触发下一场需求。
3. 人物不是属性表。人物的欲望与阻碍形成冲突，经历解释冲突，压力测试决定人物在具体情境下会怎么选。
4. 对话要有潜台词和任务。每段对话至少应刻画人物、改变关系/局势或释放必要信息，不能让人物轮流替作者讲背景。
5. 节奏是详略与压力变化，不是固定字数公式。删除无变化的场景；在关键选择、发现和后果处放慢，在重复过程处压缩。
6. 伏笔必须进入账本。记录埋设、提醒、升级、回收窗口和实际用途；伏笔还应同时承担人物、气氛或行动功能。
7. 大纲应分层且滚动。全书只固定核心承诺、人物长线变化与终局方向，卷纲在靠近执行时细化，章纲必须能直接落笔。

## 2. 目标创作流程

```text
作者心意
  -> 创作宪章（为什么写 / 留下什么 / 不可妥协 / AI 授权 / 每章验收）
  -> 三个差异化故事种子
  -> 作者选择并修改
  -> 前期人物压力测试
  -> 全书粗锚点 + 第一卷详细计划
  -> 当前章创作简报
  -> 章纲确认或自动授权
  -> 世界模拟 / 连续性守卫
  -> 初稿
  -> 独立审稿
  -> 最多三轮针对性返修，保留更好的版本
  -> Observer 状态提取 + Verifier
  -> 阻断质量门
      通过 -> 发布 Canon / Wiki / Current State / 索引 / 下一章
      失败 -> review_required，停止自动写，保留稿件供作者处理
```

人的职责是定义意义、边界和关键选择；AI 的职责是展开方案、执行写作、检查一致性和承担重复劳动。`auto_write` 只在作者明确选择“按创作宪章自动推进整卷”后开启，任何阻断门失败都会关闭。

## 3. 三种知识层的边界

### 原文证据层（RAG）

`writing_knowledge_documents` 和 `writing_knowledge_chunks` 保存源文件哈希、路径、标题路径、字符区间、标签和 1024 维向量。它回答“原资料具体怎么说”，所有建议必须能回到原文。

### 方法层（LLM Wiki 模式）

`writing_method_cards` 保存原则、适用场景、步骤、检查项、反例、互链和来源 chunk ID。它回答“现在该采用什么写法”。自动提炼的卡一律为 `draft`，作者审核为 `published` 后才可进入生成上下文；方法卡可修订，原文不可由模型改写。

这里采用 LLM Wiki 的持续编译思想，不引入桌面应用作为生产依赖。原因是故事 Wiki、用户权限、版本历史和发布事务已经在本项目中，另建第二套事实系统只会增加同步问题。

### 导航层（PageIndex 模式）

PageIndex 用于长文档或整库深度研究：先沿“目录 -> 文件 -> 标题 -> 片段”选择最小充分子树，再读取原文。每章实时写作优先使用已经编译的方法卡和混合检索，避免每章都进行昂贵的树推理。

小说自身继续使用“书 -> 卷 -> 事件弧 -> 章”的 PageIndex，处理跨卷因果、人物历史和伏笔定位。PageIndex 不是向量库，也不替代精确实体检索。

## 4. pgvector 与 Milvus 决策

当前腾讯云实例为 4 vCPU、4GiB、40GB SSD。Milvus Standalone 还需要 etcd 和对象存储，和 PostgreSQL、API、worker、前端同机时，内存余量、磁盘副本和运维复杂度都不理想。

写作指导库约 52MB，预计只有数万级片段；单本 500 万字小说按 900 字切块也约数千片段。这个量级用 PostgreSQL 的元数据过滤、FTS、HNSW 和 RRF 足够，并且可以和章节发布事务、备份、权限保持一致。

因此当前默认：

- PostgreSQL 保存 Canon、知识原文、方法卡和元数据。
- pgvector 保存 1024 维向量。
- 阿里百炼 OpenAI 兼容 Embedding 接口负责向量转换。
- PageIndex 负责树导航，LLM Wiki 方法卡负责长期知识压缩。

满足以下任一条件再迁移 Milvus：

- 活跃向量达到 50 万至 100 万并且 pgvector 实测达不到延迟目标；
- 多租户并发检索成为独立负载，需要单独扩缩容；
- 有独立的 8GiB 以上节点和至少 100GB 可监控磁盘；
- 已完成双写、离线对账、召回率基准和回滚演练。

迁移时 PostgreSQL 仍保存 source of truth，Milvus 只保存可重建向量与检索元数据。不能用 Milvus 替代事务数据库。

## 5. 阿里向量配置

生产环境必须使用独立的 Embedding Key，不与聊天模型 Key 共用；程序不会再从 `LLM_API_KEY` 回退到向量接口：

```dotenv
EMBEDDING_PROVIDER=aliyun_dashscope
EMBEDDING_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
EMBEDDING_API_KEY=从服务器密钥文件注入
EMBEDDING_MODEL=qwen3.7-text-embedding
EMBEDDING_DIMENSIONS=1024
EMBEDDING_BATCH_SIZE=16
VECTOR_STORE=pgvector
WRITING_KNOWLEDGE_ROOT=/srv/fushengliunian/writing-knowledge
```

向量模型和维度一旦用于生产 collection，不应原地修改。升级模型时建立新索引版本、后台重算、对比召回，再切换读流量。

## 6. 导入与验收

```bash
cd backend
.venv/bin/alembic upgrade head
.venv/bin/python -m app.cli.writing_knowledge \
  /srv/fushengliunian/writing-knowledge \
  --compile-cards
```

`.txt/.md/.docx/.pdf/.xls` 可直接解析。旧 `.doc/.wps` 在 macOS 可回退使用系统 `textutil`，Linux 依赖 `antiword` 或 LibreOffice；裸机部署脚本会安装体积较小的 `antiword`。不能解析的文件会以 `error` 状态和原因入库，不能计入成功数。`.chm` 建议先离线解包为 HTML/TXT 后再导入。

重复执行导入会跳过成功且内容未变化的文件，但会重试原先为 `error` 的文件；因此安装转换器后无需清库。默认报告只按阶段和扩展名汇总失败项，需要逐文件排查时再加 `--verbose-errors`。向量请求按 `EMBEDDING_BATCH_SIZE` 批量发送。

不带 `--no-embed` 执行时，导入器还会扫描历史上所有 `embedding IS NULL` 的片段并断点回填。因此可以先离线完成文本导入，轮换并配置新的阿里 Key 后再运行同一命令，不需要重建文档和方法卡。

验收必须包括：

1. 导入报告中 `files = imported + skipped + errors`，逐项处理 error。
2. `/api/knowledge/search` 返回方法卡、原文、源文件和标题路径。
3. 用人物、对话、节奏、伏笔、大纲各准备 10 个问题，评估 Recall@5 和引用正确率。
4. 生成章节时，教程建议不会出现在 Canon/Wiki 人物事实中。
5. 阻断门失败时 revision 为 `review_required`，Current State、Wiki 和下一章均不变化。

方法卡审核时以 `card_status=draft` 搜索草稿，再调用 `PATCH /api/knowledge/method-cards/{card_id}` 将状态设为 `published` 或 `rejected`。生成链只读取已发布卡；未审核的旧教程不能直接成为写作命令。

配置向量后运行 `.venv/bin/python -m app.cli.writing_knowledge_benchmark`，用仓库内 15 个固定问题记录 `heuristic_recall_at_k` 和 `citation_completeness`。这套数据用于快速发现索引或模型回归；正式验收还应把每类扩充到至少 10 题，并人工标注相关 chunk ID 后计算真正的 Recall@5。

本地实际导入结果（2026-07-23）：499 个文件中 494 个成功，形成 7,510 个可引用片段和 7,510 张待审核方法卡。剩余 3 个 CHM 需离线解包，2 个有效但本机转换器不兼容的旧 DOC 可在装有 `antiword`/LibreOffice 的 Linux 节点重试。此次未使用聊天中暴露的 Key，也未生成外部向量。

## 7. 安全约束

部署账号表和 API Key 不进入仓库、数据库、命令参数或运行日志。生产密钥文件权限使用 `0600`。已经出现在聊天记录中的 Key 应轮换后再部署。
